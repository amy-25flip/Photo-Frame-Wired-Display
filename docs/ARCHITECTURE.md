# Architecture

## The idea

The frame's boot ROM contains a USB **recovery mode (ADFU)** meant for factory firmware flashing. It accepts a small program, puts it into on-chip SRAM and runs it.
We use that to run our own code in the frame's RAM and turn the frame into a dumb display: the PC does all the work, the frame decodes frames and shows them.

```
 Windows                                            WSL2 (Linux user space)                     the frame
 ─────────────────────────────────────────────      ─────────────────────────────────────      ─────────────────────────────
 virtual display (signed VDD) ─ capture (mss)       frame_sender.py (pyusb over usbipd)        boot ROM ─ ADFU
 mirror.py: crop/scale ─ 12-bit pack (c444.py) ───▶ stage-1 upload, blob load, frame stream ──▶ stage 1 (2 KB, SRAM)
 frame_watcher.py: plug detection, mode switch,                                                  stage 2 (DRAM, I-cache)
   session control, virtual display attach                                                       LCD controller + display engine
```

## USB identities and startup

* Plugged in normally the frame is a mass-storage device `10d6:1101`. The vendor SCSI command `CB 21 00 00 00 00 00 00 02 00 00 00` (length big-endian at CDB bytes 7–8,
  expected reply `FF 00`) followed by START STOP UNIT (eject) makes it re-enumerate as ADFU `10d6:10d6` (see `win_enter_adfu.py`; it only talks to storage devices that descend from
  a live `VID_10D6&PID_1101` USB node and never ejects after a failed or unacknowledged command). Holding MENU while plugging in goes to ADFU directly.
* ADFU protocol (BOT-style framing): 31-byte CBW `USBC` on EP1 OUT, optional data, 13-byte CSW `USBS` on EP2 IN. `GetInfo` = CDB `0xCC`, upload = CDB `0x05`
  with address/length and data in 512-byte chunks, execute = CDB `0x10`. Our code is loaded at the SRAM window **0xB4061000, 2 KiB**. The loader library is
  [actions-adfu-tool](https://github.com/BlackLikeaCat/actions-adfu-tool) (GPL-2.0+).

## Stage 1 (`v100display/stage1.py` → `stage1-clean.bin`, 2 KiB)

Generated by a small Python assembler (`mipsasm.py`-style macros inside the script); `python stage1.py sim` runs it in the Unicorn emulator against a fake USB FIFO,
`dump out.bin` writes the image uploaded to the frame. It:

1. disables interrupts (the ROM's USB handler must not steal the FIFO), clears both 1024×600 RGB565 framebuffers *before* any panel/backlight setup (no stray pixels),
2. brings up the LCD controller (CMU/GPIO/LCD/PWM tables) and the display engine (`DE_PLANE0_*`, base 0xB02F0000),
3. receives 512-byte bulk-OUT packets by reading the endpoint FIFO port (0xB0290084, one 32-bit pop per load) and hunts for a header (self-synchronising),
4. understands three header types (all start with the same four magic words, word 0 differs):
   * `V1HD` frame/band update: rows `y0..y0+rows` of RGB565 into the back buffer; unless the "no flip" bit is set, flips `DE_PLANE0_BA` and acks `FMR4`,
   * `V1CM` command: up to 8 register pokes (byte writes by address flag) and 4 peeks per packet, acked `CMD1` with the peek values — this is the debugging/bring-up channel,
   * `V1XQ` loader: copy *N* packets to a DRAM address, invalidate both caches (Index_Store_Tag), optionally call it (`jalr`, kseg0 so it runs from the I-cache), ack `XQD1` when it returns.
   The first ack after loading is `RDY1`.

## Stage 2 (`v100display/s2_c444.py`, a blob loaded with `V1XQ`)

Runs from DRAM through the I-cache. Per 512-byte packet: arm the OUT endpoint, wait for the packet, start a **system-DMA** copy from the FIFO port into a staging slot
(DMA mode `0x00120052`: source treated as plain memory with a fixed address; the USB DRQ line does not fire), and while the DMA runs decode the *previous* packet.
The decoder unpacks 8 pixels per 12 bytes and maps each 12-bit code through a 4096-entry RGB565 lookup table kept in the data cache, storing to the back buffer.
After the last packet of a frame it flips `DE_PLANE0_BA`, acks `C4F1` and goes back to hunting for the next `V1C4` header. `V1ST` makes it restore S0–S7 and return to stage 1.

**12-bit format** (`v100display/c444.py`): code = R4<<8 | G4<<4 | B4, 4×4 ordered (Bayer) dither on the PC, eight pixels = 96 bits = 12 bytes little endian,
42 groups per 512-byte packet (504 data bytes + 8 padding), 1829 packets (936,448 bytes) per frame instead of 2400 packets (1.2 MB) raw RGB565.

## Why it is shaped like this (measurements on the verified unit)

| finding | number |
|---|---|
| USB high-speed bulk link ceiling (host → device, no FIFO reads) | ≈ 41 MB/s (~33 fps of raw RGB565) |
| Reading the endpoint FIFO port, CPU loop (uncached code) | ≈ 22 fps raw (27 MB/s) — **limited by instruction fetch**, not the port |
| Same CPU loop's instruction speed: uncached SRAM/DRAM code vs code in the I-cache | **17 MIPS vs 366 MIPS** (57 ns vs 2.7 ns per instruction) |
| Pure DMA read rate of the FIFO port | ≈ 30 MB/s (16.5 µs per 512 B) — the hard ceiling |
| DRAM: uncached load / uncached store / D-cached copy | ~290 ns per word / ~19 ns per word / 78 MB/s |
| Final: 12-bit stream, DMA + decoder overlap | **29.6–33.5 fps**, ~31 MB/s of packed data, decode hidden under the DMA |

Things that were tried and did **not** help (details in [RESEARCH_NOTES.md](RESEARCH_NOTES.md)): USB-DRQ-triggered DMA, arming the next packet during a DMA, reading
past one packet (hangs the controller), a second DMA channel (channel 4 hung the USB block), cached-framebuffer writes alone, the display's overlay/YUV plane
(registers accept writes, nothing renders), reading the SD slot (the controller never sees the card without pin-mux knowledge we do not have).

## Display engine facts used

`DE_ENABLE` 0xB02F0000, `DE_PLANE0_CFG` +0x40 (0x40000 normal; 0xC0000 = hardware 2× zoom, used by the old low-resolution "turbo" mode), `DE_PLANE0_BA` +0x50
(flip), `DE_PLANE0_STRD` +0x70. Register map credit: [SiarheiVolkau/actions-hacking](https://github.com/SiarheiVolkau/actions-hacking).

## Host side

* `frame_watcher.py` – polls `usbipd state`, switches normal → ADFU (`win_enter_adfu.py`), attaches to WSL, runs the *clean* startup sequence
  (`fast_bootstrap.py` + `show_loading.py` via `load_clean_receiver.py`: upload stage 1, wait `RDY1`, show the loading picture in one flip), starts `frame_sender.py --c444`
  (uploads stage 2 **verified by RAM readback** before executing it, waits `C4RD`, sends the loading picture in packed form, waits `C4F1`), attaches the virtual display
  (`display_manager.py`), starts `mirror.py`. Any unexpected state stops the session instead of blindly retrying; unplug/replug retries.
* `mirror.py` – captures the virtual monitor at native size (identical frames are not sent), packs with `c444.py`, sends frames over TCP to the sender.
* Startup lessons are baked in: send a junk packet first (the first packet after load can be lost), never use short-timeout flush reads, finish a command/ack round trip
  before queueing the first code packet, keep WSL alive while the stub runs, never reload over a running stub.
